# Workforce failure analysis

## Evidence reviewed

The reported room transcript shows that Caveworkers creates a rich-looking collaboration trace for tasks, but the trace is primarily generated by `handleTaskRoutingAsync` rather than being the result of completed external work. For email requests, the current code intentionally creates a pending approval and emits `No external tool has been called.` The approval endpoint only changes the record state; it does not dispatch an approved workforce action. Gmail is provisioned with `gmail.readonly` and `gmail.search` only, so Sarah cannot send mail even if approval is granted.

Task routing currently picks a keyword winner or defaults to Alex. Sarah is catalogued as Talent & HR Manager but has no universal manager authority and is not the workflow lead for every team request. The current fallback answer is a role-based recommendation brief and the frontend renders the trace but does not surface `task.answer` as the primary final response. The result is a simulated-feeling room, unclear completion, and no user-visible answer to the actual request.

The room CSS also uses compact 8–13px typography for high-value content, making the workflow difficult to read and use.

## Corrected operating model

1. Sarah is the **Workforce Manager** and default orchestration lead for the whole Caveworkers team. She delegates domain work to the other active employees and consolidates the final response.
2. Direct employee assignment remains supported. Whole-team assignment means Sarah coordinates the active workforce, with the selected employee group shown explicitly.
3. Every task has explicit states: queued, working, waiting for approval, completed, failed, and completed-with-action. A task is not marked completed while it is only a draft or waiting for an external action.
4. The final answer is a first-class task result and must be shown prominently in the company room. The collaboration trace is supporting evidence, not the answer.
5. External actions are approval-gated but executable after approval. The approval record carries a structured action request, and approving it triggers a tenant-scoped dispatcher with idempotency protection and visible success/failure outcome.
6. Gmail sending requires a separate opt-in write scope, explicit connector grant, recipient/message preview, manager approval, and audit logging. Existing read-only Gmail connections must not silently gain write access; users must reconnect/upgrade the connector.
7. If a connector or permission is unavailable, Sarah must tell the user exactly what is missing and stop with an actionable status rather than pretending the work is complete.
8. The UI should prioritize task result, current state, next action, and approval controls with readable typography and less decorative trace density.

## Required implementation areas

- Add Sarah-manager routing and delegation semantics.
- Add structured workforce action payloads and an approved-action dispatcher.
- Add Gmail send capability with explicit OAuth scope and per-connection write grant.
- Make approvals update the related task state and execute or fail visibly.
- Surface final task answers and clear state cards in the room.
- Increase room typography and remove low-value density.
- Add tests for Sarah leadership, pending-to-completed action transitions, Gmail scope/grant checks, missing connector behavior, and final-answer rendering data.
